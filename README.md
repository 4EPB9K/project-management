# «Четверть» — CRM для проката лёгкого транспорта

**Учебный проект по дисциплине «Проектный менеджмент»**  
Воронежский государственный университет · Факультет компьютерных наук · Команда № 23 · Группа 25 · 2026

> **Назначение репозитория:** материалы пяти учебных фаз по выбору концепции, распределению работ, оценке трудоёмкости, прогнозированию и планированию проекта. Это репозиторий **проектно-аналитических материалов**, а не готового программного продукта.

## 1. О проекте

**«Четверть»** — концепция внутренней CRM-системы для компании, которая сдаёт в аренду велосипеды, обычные и электрические самокаты. Название связано с идеей доступного транспорта и коротких городских поездок в пределах «15-минутного города».

Цель системы — объединить в одном интерфейсе учёт транспорта, клиентов, точек проката, аренд, платежей и технического обслуживания. Сотрудники должны видеть, где находится единица транспорта, доступна ли она к выдаче, закреплена ли за клиентом или находится в ремонте.

**Основные роли:**

- **Администратор** — управляет парком транспорта, точками проката и отчётностью.
- **Менеджер проката** — регистрирует клиентов, проверяет доступность, оформляет выдачу, возврат и оплату.
- **Механик** — фиксирует неисправности, работы по обслуживанию и возвращает транспорт в доступный парк.

**Основной процесс:** транспорт и клиент заносятся в систему → менеджер проверяет доступность → оформляет аренду и выдачу → рассчитывает стоимость и регистрирует оплату → оформляет возврат → при необходимости направляет транспорт на обслуживание.

### Границы MVP

В учебной модели рассматривается **внутренняя CRM одной прокатной компании**. Базовый контур включает реестр транспорта и точек проката, карточки клиентов, поиск доступных единиц, выдачу и возврат, тарифный расчёт, **ручную регистрацию платежей**, ремонт и базовую отчётность.

В базовом объёме **не предусматриваются** нативное мобильное приложение, автоматическая интеграция с платёжным шлюзом, онлайн-карта GPS-позиций и сложное динамическое ценообразование. Эти возможности могут рассматриваться как отдельное развитие продукта.

## 4. Фаза 1 — выбор концепции

Сопоставлены четыре идеи: **TaskFlow**, **MoneyTrack**, **«Четверть»**, **BookEasy**. Критерии: реализуемость MVP, практическая полезность, ясность требований и потенциал развития.

- **Нечёткий коллективный TOPSIS:** трёхточечные оценки (пессимистичная, ожидаемая, оптимистичная), расчёт расстояний до положительного и отрицательного идеалов и коэффициента относительной близости.
- **Чёткий коллективный МАИ (AHP):** попарные сравнения по шкале Саати, определение весов, проверка согласованности матриц и итоговых приоритетов.

| Место | Концепция | TOPSIS (CC) | МАИ (вес) |
|---:|---|---:|---:|
| **1** | **Четверть** | **0,779** | **0,342** |
| 2 | TaskFlow | 0,472 | 0,270 |
| 3 | BookEasy | 0,282 | 0,195 |
| 4 | MoneyTrack | 0,213 | 0,193 |

Оба метода в текущем наборе исходных оценок дают одинаковое ранжирование. Концепция **«Четверть»** выбрана для дальнейшей проработки.

## 5. Фазы 2 и 3 — связанные расчёты

По методике дисциплины **сначала определяется состав работ фазы 3**, затем в фазе 2 решается задача их оптимального распределения, после чего выполняется сама оценка проекта.

### Фаза 2. Оптимальное распределение учебных работ

Работы третьей фазы разложены на задачи `T01–T12`. Для них заданы оценки трудоёмкости и предпочтительности назначения каждому участнику. В модели используется бинарная переменная `xᵢⱼ`, равная 1, если задача `i` назначена участнику `j`, и 0 иначе.

**Целевая функция:** максимизация суммы предпочтений при ограничениях «один основной исполнитель на задачу», индивидуальных бюджетов времени и минимальной вовлечённости каждого участника. Решение получено целочисленной оптимизацией; контроль выполнен перебором вариантов.

| Показатель | Результат |
|---|---:|
| Задач учебной фазы 3 | 12 |
| **План** на подготовку фазы 3 | **30 чел.-ч** |
| Плановая нагрузка Александра / Ильи | 15 / 15 ч |
| Количество назначенных задач | 6 / 6 |
| Максимальная сумма предпочтений | **53 балла** |
| Рассмотрено бинарных назначений | 4 096 |

**Материалы:** [папка фазы 2](phase-2/) · [общая Excel-книга](phase-2/phase-02-calculations.xlsx) · [Python-оптимизатор](phase-2/phase-02-solver.py) · [отчёт](phase-2/phase-02-report.docx).

### Фаза 3. Оценка разработки CRM

Оценивается **потенциальная разработка системы**, а не время, затраченное студентами на выполнение учебных расчётов.

- **COSMIC:** функциональные перемещения групп данных `Entry / Exit / Read / Write`.
- **UCP:** веса акторов и вариантов использования, технические и средовые факторы.
- **Коллективная экспертная оценка:** оценки трудоёмкости функций, агрегированные по принятому в работе правилу.

| Метод | Расчётный результат | Ориентировочные трудозатраты разработки |
|---|---:|---:|
| COSMIC | **84 CFP** | 1 344 чел.-ч при 16 ч/CFP |
| Use Case Points | **114,92845 UCP** | 1 379,14 чел.-ч при 12 ч/UCP |
| Экспертный метод | Сумма оценок по функциям | 1 245 чел.-ч |
| **Сводный сценарий** | Веса методов 35% / 35% / 30% | **≈ 1 326,60 чел.-ч** |

Коэффициенты перевода CFP и UCP в часы, а также веса сводного сценария — **допущения учебной модели**, а не нормативы COSMIC/UCP. Результат предназначен для оценки масштаба, предварительного состава команды и календарного планирования.

**Материалы:** [папка фазы 3](phase-3/) · [общая Excel-книга](phase-3/phase-03-calculations.xlsx) · [отчёт](phase-3/phase-03-report.docx).

### Почему Excel повторяется в двух фазах

Для фаз 2 и 3 используется **одна общая книга на 14 листов**, так как исходные данные и расчёты связаны. В репозитории она размещается под двумя названиями — `phase-02-calculations.xlsx` и `phase-03-calculations.xlsx`. При изменении исходных оценок следует **одновременно обновить обе копии** и связанные отчёты.

**Не смешивать два вида времени:** `30 чел.-ч` — план подготовки **учебной третьей фазы**; `≈ 1 326,60 чел.-ч` — условная оценка **разработки самой CRM**.

## 6. Дальнейшие этапы

### Фаза 4 — прогнозирование

Сначала декомпозируются работы фазы 5, затем для них задаются пессимистичная, наиболее вероятная и оптимистичная продолжительности. Прогноз срока выполняется методом Монте-Карло двумя способами:

1. По эмпирическому распределению **числа завершённых задач за неделю**.
2. По распределению **доступных человеко-часов в неделю** с треугольными распределениями продолжительностей задач.

В обоих случаях определяется срок с **80%-ным уровнем надёжности**, а различия моделей анализируются. Входные распределения следует строить на данных реального учёта предыдущих этапов из YouGile.

### Фаза 5 — планирование

Формируется перечень примерно **20–25 работ** по реализации «Четверти», указываются длительности, предшествования и потребность в ролях (разработка, тестирование, дизайн и др.). План строится при ограничениях ресурсов, сравниваются эвристики упорядочения и случайно сформированные варианты. Лучший график переводится в стандартный режим **8 часов в день, 40 часов в неделю**.

## 7. Как воспроизвести расчёты фазы 2

Для запуска оптимизатора нужен Python 3 и библиотеки **NumPy** и **SciPy**. Из корня репозитория:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install numpy scipy
python phase-2/phase-02-solver.py
```

Скрипт решает задачу распределения и проверяет назначение на ограничения. Числовые результаты должны совпадать с разделами `Ф2_...` общей книги Excel при тех же исходных оценках.

- В расчётных книгах используются **предварительные учебные экспертные оценки**. Они не равны фактически отработанным часам и не должны представляться как независимые анкеты без подтверждения участников.
- **Контроль согласованности фазы 3:** в текущем Word-отчёте каталог пронумерован `UC02–UC12` (11 явно описанных Use Cases), тогда как сводные разделы заявляют 12. Перед окончательной сдачей нужно восстановить отсутствующий `UC01` и проверить связанные расчёты COSMIC, UCP и экспертных часов либо согласованно пересмотреть каталог и итоги. **Текущие значения выше — результаты имеющейся версии расчётной книги.**
- После изменения исходных данных проверяются итоговые таблицы, формулы, два экземпляра общей Excel-книги и соответствие Word-отчётов.
- Использование LLM должно соответствовать ограничениям официального задания: для фазы 1 — генерация концепций и критериев; для других фаз — допустимая помощь в коде и анализе с самостоятельной проверкой результата.
